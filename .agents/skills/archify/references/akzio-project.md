# Akzio project map

Use this overlay only for diagrams of `akzio-signal-intelligence`. Read the relevant sections indexed by the repository `AGENTS.md`, then follow actual Rust call sites and frozen Contract consumers. This reference is a **map of questions to verify**, not a substitute for source citations and not a frozen list of current version numbers.

## One integrated artifact, honest evidence

- Keep exactly one Akzio diagram deliverable: one candidate and one standalone HTML in `.archify/akzio-process/`, including focused policy/Outcome follow-ups. Integrate the new slice into its views/cards or revise the same map rather than create another timestamped output. Preserve current delivery and check receipts. Only an explicit user request to change the one-artifact rule permits a separate version.
- Freeze a credential-free origin and a Git revision as in [Repository authoring](repository-authoring.md). For this project, publish **file-level** `sources` (`path` and, where useful, a semantic symbol/role `label`); omit `line` and `end_line`, line fragments, `path:line` text and numbered source positions from the candidate, HTML cards and companion docs. Trace precise call sites privately while authoring, but do not make moving line offsets the reader's navigation contract. If the worktree is dirty, these source files and Archify provenance describe **committed bytes at that revision**. Inspect committed bytes for changed paths; do not describe the dirty tree as that commit or imply that the diagram is a live Core/Store view. If a working-tree-only change is essential, state its unverified provenance separately rather than silently attaching it to the committed revision.
- When refreshing the map or companion reports, scan `.archify/akzio-process/candidate.json`, the generated HTML and `docs/` for line fragments (`#L` followed by digits), source `file.ext:number` positions, and candidate `line` / `end_line` keys; remove them before delivery. Check file existence and relative Markdown links separately. File-only navigation reduces offset drift but **never** proves that a changed implementation still has the described behavior.
- When the user asks to consolidate outputs, verify the replacement candidate, HTML, provenance and local inbound links **before** removing only the obsolete generated artifacts they named. Never erase an unrelated diagram, Store, BLOB, report, socket, configuration or credential as routine cleanup. A repeated delivery to the same HTML still follows the skill's failed-gate and existing-output recovery contracts.
- A single HTML can carry multiple guided views and explanatory cards. Keep the T0 and historical Outcome paths distinguishable in the topology; use cards for detailed conditions and formulas rather than drawing misleading unconditional arrows. The Viewer is an **offline, source-backed observability map**, not telemetry, approval, an account snapshot, or Paper/Outcome validation.

## Control and timeline questions to verify

| Slice | Required distinction in the diagram |
|---|---|
| Entry and evidence | App/CLI is a client, Rust Core is the authority. Formal Paper uses a real session, unique slot and bounded EvidenceNeed; PositionPlan has a different graph ending after Decision. Debug Store, Broker policy and learning eligibility are independent isolation controls. |
| Research and review | EvidenceGate → authorized `akzio-context` projection → three horizon Analyst/Critic paths → bounded supplement/refinement → Synthesizer's four-assets × three-horizons forecasts and research allocation → exact-proposal Review. Model output and Reviewer acceptance do not become a tradable target or execution permission. |
| Policy cold start | SQL active head absent means a fail-closed default, **not** an implicitly selected candidate. A canonical Paper cold-start Run can finish `NoOrder` and, with a valid frozen baseline, schedule real Outcome; PositionPlan and isolated Debug cannot be relabeled as canonical calibration data. |
| Historical policy production | `OutcomeSchedule` advances independently through four-assets-common T+1/T+3/T+5 trading sessions; sealed price labels are not order fills or later account NAV. Read-only readiness, operator-supplied risk limits, eligible canonical dataset collection, offline fit, inspection/validation, and explicit activation are distinct transitions. A candidate is not an active head. |
| Next T0 target | An active, compatible Policy is a process-loaded snapshot, not a per-Decision retrain. One Policy holds 12 horizon/asset calibration surfaces and asset/portfolio risk. A **new** reviewed 12-forecast proposal goes through exact bin/sample/Brier/age qualification, neutral/uncalibrated/conflict rules, horizon-weight and leveraged-holding filters, asset caps and portfolio caps; distinguish `research_allocation` from formal `Decision.targets` and its trace. An active Policy does not imply every raw probability bin is qualified. |
| Paper and later results | Decision → fresh ExecutionGate snapshots, original approval and blockers → `NoOrder` or `Accepted` → durable Commitment before authorized Paper I/O → broker acknowledgment/fill and Reconciliation as separate facts → Evaluate schedule → independent partial/final Outcome and gated learning. Zero target is not permission to liquidate without Gate; PositionPlan does not traverse Paper/Outcome nodes. |
| Authority and display | `V2Store`/CAS is the durable authority and Observatory exposes bounded projections. Show eligibility, current Run facts and missing evidence as distinct from source-defined reachability. Do not turn a source diagram into a claimed real-Paper fill or completed T+5. |

For the current behavior and vocabulary, verify the relevant `docs/agent-runtime-contract.md` §§3, 7, 8, 11, 12, `docs/development-workflow.md` calibration/readiness and verification guidance, and the real CLI/Store/DecisionGate/ExecutionGate/Outcome implementation. Do **not** freeze today's sample counts, model dates, Contract numbers, order states or policy hashes into this reusable skill. Do not run Core, models, calibration writes, Paper API, or production Store reads merely to draw a diagram; those are separate, authorization-sensitive tasks.

## Delivery language

Report diagram schema/static validation, artifact provenance, automated browser result, and human visual inspection **separately**. A browser gate skipped for missing Chrome remains skipped even if `validate`, `deliver`, and strict `check` pass; never call that a passing `finalize` or a visual review. Link any companion report to the one maintained HTML, and note when its working-tree reading and the diagram's pinned commit have different evidence scopes.
